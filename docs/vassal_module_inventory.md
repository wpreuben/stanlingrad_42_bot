# VASSAL 2.03 모듈의 구조화 자료 조사

조사 대상: 저장소 루트의 `Stalingrad42_v203/` (사용자 제공 자료). 이 폴더는 압축을 푼 VASSAL 2.03 모듈이다. 아래 결과는 기본 영문 규칙서 v2.1의 규칙 판정과 별개로 원본 자료를 조사한 것이다.

## 바로 사용할 수 있는 자료

| 파일 | 확인된 내용 | 엔진에 쓸 수 있는 범위 |
|---|---|---|
| `buildFile.xml` | Map A를 포함한 4개 게임 보드의 이미지 연결, 헥스 격자 원점·간격·번호 설정, 카운터 `gpid`와 이름·이미지·특성, 시작 카드·증원 디스플레이의 스택 | 지도 좌표 보정, 카운터 목록·이미지 연결, 카드 구성의 대조 자료 |
| `S1.vsav`–`S4.vsav` | 각 시나리오의 게임 상태. 해독하면 일부 맵 위 카운터의 위치, `gpid`, 과거 헥스 번호가 드러남 | 시나리오 배치 검수의 보조 자료. 디스플레이에 남은 카운터는 지도 위 헥스 배치로 간주하면 안 됨 |
| `images/Stal42_Map_west-FINAL-150 Q12.jpg` | Map A의 3300×5100 JPEG | 기존 지도 이미지와 동일한 픽셀 자료 |

`buildFile.xml`의 Map A 보드에는 헥스 격자 `dx=98.8550992617019`, `dy=113.90000000000046`, `x0=27`, `y0=23`이 있다. 이 값은 최근에 99픽셀로 보정한 가로 간격을 뒷받침한다. VASSAL Map A JPEG와 `images_high/Stal42_Map_west-FINAL-150 Q12.jpg`의 SHA-256은 둘 다 `7a3b5b6a075021bcb7bfc7da2f7e274feee79f8bafec15f967a062bcf380ef47`이다.

`.vsav`는 ZIP이며 내부 `savedGame`은 `!VCSK` 다음의 한 바이트 키와 16진수 본문으로 구성된다. 본문을 16진수로 변환해 그 키로 XOR하면 `begin_save`로 시작하는 텍스트가 나온다. 예를 들어 S1의 키는 `aa`다. S1의 맵 위 기록 한 건은 `gpid=1816`, `OldLocationName=2602`이며, `buildFile.xml`의 `gpid=1816`은 `SO 2 TD Div`다. 이는 저장 파일과 카운터 정의가 실제로 연결됨을 검증하는 사례다.

현재 단순 추출로 확인한 맵 위 **숫자 4자리 헥스 위치** 기록은 S1 16건, S2 8건, S3 23건, S4 29건이다. S1에는 `Main Map` 소속 기록이 179건 있지만 다수는 `E1` 같은 엔트리 구역 등 숫자 헥스가 아닌 위치다. 이 숫자는 시나리오의 전체 유닛 수나 모든 초기 배치의 완전성을 의미하지 않는다. 저장 상태·시작 카드·규칙서의 차이를 대조한 뒤 사용해야 한다.

## 지도 지형 자료의 한계

모듈 정의에서 헥스 격자(`HexGrid`)와 좌표 번호(`HexGridNumbering`)는 확인했으나, 헥스별 지형, 강변, 도로, 철도, 교량을 기록한 태그·별도 데이터 파일은 확인하지 못했다. `Zone`은 대부분 화면의 트랙·엔트리 구역·디스플레이 영역이고, `Hexgrid` 존도 격자의 위치를 정의할 뿐 지형을 분류하지 않는다. 따라서 이 모듈만으로 `map_a.json`의 지형과 변 속성을 자동으로 완성할 수는 없다. 지도 지형은 JPEG에서 읽고 검수해야 한다.

## 권장 다음 작업

1. 모듈 격자 설정을 지도 이미지 보조 도구의 좌표 보정 검증값으로 사용한다.
2. `buildFile.xml`의 카운터 `gpid`·이름·이미지와 S1–S4 저장 파일의 배치 정보를 **출처를 표시한 후보 자료**로 추출한다. 저장 파일의 맵/시작 카드/엔트리 구역 위치를 구분한다.
3. 지형과 변 속성은 기존 이미지 검수 절차를 유지하되, 수작업 범위를 줄일 다른 구조화 자료가 있는지 별도로 확인한다. 2.03 모듈과 2025년 v2.1 규칙서의 차이는 그대로 채택하지 않고 대조한다.
